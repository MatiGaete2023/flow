## Revisión del 10 de octubre: concurrencia y presupuesto de CI

**Hallazgo.** Desde las 03:24 UTC, GitHub Actions dejó de asignar runners, probablemente por los minutos de Windows
(no verificado). La causa más probable es esta combinación:
- Concurrencia: el grupo `workflow-rama` era el mismo para el push y para el PR, y con `cancel-in-progress` uno
  cancelaba al otro. El orden no es determinista, así que a veces el PR quedaba «cancelled».
- Los 14 PR apilados relanzaban la matriz completa (×3 versiones, Windows ×2 minutos) en cada propagación.

**Cambio (desvía la ficha; propuesta P2-a del reporte de revisión):**

| Aspecto | Antes | Ahora |
| --- | --- | --- |
| Push | `main`, `feat/**`, `wp/**` | Solo `main` y `feat/**`; las ramas `wp/**` se prueban en su PR |
| Matriz en PR | 3.12, 3.13, 3.14 | 3.12 |
| Matriz en push a `feat/**` o `main` y en `workflow_dispatch` | 3.12 | 3.12, 3.13, 3.14 |
| Grupo de concurrencia | `workflow-rama` | `workflow-evento-rama`: un push y un PR ya no se cancelan entre sí |

**Aceptación que reemplaza «un push a `wp/**` corre solo 3.12»:**
- un PR corre solo 3.12;
- el push de integración a `feat` corre la matriz completa.

`test_current_release_contract.py` lo exige.
