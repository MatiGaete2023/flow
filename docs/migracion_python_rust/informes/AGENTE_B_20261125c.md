## 5. Hallazgos

**Hechos.**

- `run_por_hoja` de Python, con menos de dos pestañas, devuelve `[run(...)]`: un solo paquete. Se reprodujo y hay una
  prueba (`por_hoja_de_una_hoja_igual_a_run`) que compara el proceso y el ZIP del flujo por hoja con los de `run`.
- `informes` se activa solo en la hoja «Cumplimiento» (red de seguridad: `opciones.informes && hoja == "Cumplimiento"`);
  el resto de las opciones viaja igual a cada hoja.
- Una hoja que falla emite el aviso «La hoja {hoja} no se pudo completar: {error}» y sigue con la siguiente; si todas
  fallan se devuelve el primer error. Si la falla ocurre con la cancelación pedida, el error se propaga (y no se
  devuelven paquetes), como en Python.
- El caso de cancelación fija el comportamiento real de Python: la primera hoja queda completa, la segunda cortada y
  `retomar` la termina en su carpeta. El oráculo guarda la entrada de la hoja cortada y el resultado de retomarla.
- Diferencia declarada: Python atrapa solo `PocError` (un `OSError` de escritura aborta todo el flujo por hoja); Rust
  no distingue la clase del error y trata cualquier falla de una hoja como recuperable. El efecto visible es el mismo
  («una hoja que falla no impide las siguientes») y no se toca la referencia.

**Inferencias.** Cada hoja escribe en su propia carpeta con marca de microsegundos; dos hojas del mismo run no colisionan
en la práctica (cada una tarda al menos una consulta y una descarga). Si el reloj devolviera el mismo microsegundo en dos
arranques seguidos, la segunda hoja reutilizaría la carpeta de la primera; no se agregó un sufijo porque Python tampoco lo
hace y el oráculo compara nombres normalizados.

**Especulación.** Con muchas pestañas el avance de las fases se encadena en el mismo registro; si el usuario quiere
distinguir el avance por hoja, los eventos `Estado` («Hoja N de M») ya lo permiten y la vista los muestra en orden.
